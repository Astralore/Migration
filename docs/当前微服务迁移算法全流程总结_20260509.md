# 当前微服务迁移算法全流程总结

> 基于当前代码库 `Migrate-main` 的主线实现整理，重点覆盖数据准备、仿真模拟、轨迹预测、上下文感知、奖励建模以及实际迁移算法。本文档描述的是当前 `run_comparison.py`、`core/`、`prediction/`、`algorithms/` 中正在使用的实现，不再沿用早期 `reference/` 或旧文档中的单体服务迁移口径。

---

## 1. 总体架构

当前系统把“移动用户接入边缘服务器”问题扩展为“每个移动用户携带一个微服务 DAG，DAG 内多个微服务节点可分别部署到不同边缘服务器”的协同迁移问题。

主流程如下：

```text
出租车轨迹数据
  -> 数据清洗 / 活跃车辆筛选 / episode 切分
  -> 按 taxi_id 做训练 / 测试拆分
  -> 轨迹预测器拟合
  -> 时间步仿真
  -> 每辆车维护一个微服务 DAG 与节点部署状态
  -> SLA / 预测触发迁移决策
  -> SA、DQN、Hybrid SAC 分别给出 DAG 节点放置
  -> 奖励、迁移次数、违规次数、时延、成本拆分评估
```

核心入口是 `run_comparison.py`：

- `run_training_phase(...)`：加载数据，按车辆 ID 切分训练/测试，在 `train_df` 上训练 SA、DQN、Hybrid SAC 的 proactive/reactive 两组实验。
- `run_inference_phase(...)`：重新只在 `train_df` 上拟合预测器，在 `test_df` 上加载 checkpoint 做推理评估。
- `--pipeline` 模式：删除旧 SAC 权重，完整执行训练 -> 推理 -> 生成 `result.md` -> 生成图表。

核心模块分工：

| 模块 | 文件 | 职责 |
|---|---|---|
| 数据准备 | `core/data_loader.py` | 轨迹清洗、Top-N 活跃车辆筛选、episode 生成、已清洗 CSV 快捷读取 |
| 轨迹预测 | `prediction/simple_predictor.py` | 当前迁移算法实际使用的轻量速度预测器 |
| 地理与物理模型 | `core/geo.py`、`core/physics_utils.py` | Haversine 距离、最近边缘服务器、传播/接入时延 |
| 上下文触发 | `core/context.py` | Reactive / Proactive 迁移触发判断 |
| DAG 建模 | `core/microservice_dags.py`、`core/dag_utils.py` | 微服务拓扑、入口节点、拓扑排序、初始部署 |
| 状态构建 | `core/state_builder.py` | DQN 向量状态与 Hybrid SAC 图状态 |
| 奖励函数 | `core/reward.py` | 接入、迁移、通信、tearing、future、SLA 等总成本计算 |
| 迁移算法 | `algorithms/sa.py`、`algorithms/dqn.py`、`algorithms/hybrid_sac.py` | 三类主算法 |
| 评估展示 | `evaluation/metrics.py`、`evaluation/plot.py` | 排名、Proactive/Reactive 对比、训练曲线和成本图 |

## 2. 数据准备流程

### 2.1 输入数据

默认输入路径定义在 `core/data_loader.py`：

- 出租车轨迹：`data/taxi_with_health_info.csv`
- 边缘服务器：`data/edge_server_locations.csv`
- 预处理轨迹：`data/processed/taxi_cleaned_active100_min100_eps2h.csv`

虽然原始文件名包含 `health_info`，但当前 `load_data(...)` 的主线实现只保留物理移动列：

```text
taxi_id, date_time, latitude, longitude
```

也就是说，当前上下文感知主要来自物理距离、QoS、预测轨迹、DAG 拓扑和触发类型，不再使用年龄、健康风险等早期上下文字段。

### 2.2 原始清洗管线

当 `processed_csv` 不存在，或显式传入 `processed_csv=False` 时，会执行完整清洗：

1. 读取 CSV，并只保留 `taxi_id`、`date_time`、`latitude`、`longitude`。
2. 将 `date_time` 转为时间类型，按 `taxi_id/date_time` 排序。
3. 删除经纬度缺失点。
4. 对同一车辆同一时间戳去重。
5. 按车辆逐轮清除速度跳变点，默认阈值 `v_max_kmh=200.0`。
6. 剔除轨迹点数过少车辆，默认 `min_vehicle_points=100`。
7. 选取最活跃 Top-N 车辆，默认 `active_users_limit=100`。
8. 基于时间间隔生成 `episode_id`，默认同车相邻点间隔超过 `2h` 就开启新 episode。
9. 可选按行切片或 `chunk_size` 截断。

`export_cleaned_corpus(...)` 会把上述结果导出到默认预处理 CSV，后续实验可以跳过重复清洗。

### 2.3 已清洗 CSV 快捷路径

当前主实验默认传入 `DEFAULT_PROCESSED_TAXI_PATH`。如果该文件存在，`load_data(...)` 直接读取：

```text
data/processed/taxi_cleaned_active100_min100_eps2h.csv
```

读取后会验证必要列：

```text
taxi_id, date_time, latitude, longitude, episode_id
```

这种路径可以显著缩短重复实验启动时间，但也意味着如果调整了速度阈值、Top-N 或 episode 参数，需要重新导出预处理文件，否则实验仍会使用旧清洗结果。

### 2.4 训练 / 测试拆分协议

`run_comparison.py` 使用 Strategy B：

- 先加载活跃 Top100 且每车不少于 100 点的数据。
- 使用 `default_rng(42)` 对唯一 `taxi_id` 做随机打乱。
- 按车辆 ID 而不是按行做 80/20 拆分。
- `train_df` 和 `test_df` 的车辆集合互不相交。

该设计避免同一辆车的轨迹同时出现在训练和测试中，降低数据泄漏风险。预测器也只在 `train_df` 上 `fit(...)`，推理阶段只在 `test_df` 上运行迁移仿真。

## 3. 仿真模拟机制

### 3.1 时间步驱动

三个算法的主循环结构基本一致：

```text
按 date_time 排序得到所有时间步
按 date_time groupby
for timestamp in timestamps:
    for row in current_rows:
        读取 taxi_id / latitude / longitude
        如果是新 taxi：
            选择最近边缘服务器
            随机分配一个 DAG 类型
            将该 DAG 所有微服务节点部署到最近服务器
            记录上一位置
            continue
        否则：
            找到该 taxi 的 DAG、入口节点、当前 gateway 服务器
            计算用户到 gateway 的距离与 SLA 状态
            如启用 proactive，则预测未来位置
            调用 get_trigger_type(...)
            无触发则跳过
            有触发则获取 k=3 最近候选服务器
            调用具体算法更新 DAG 节点部署
            计算 reward / cost / migrations / violations
            更新上一位置缓存
```

每个 `taxi_id` 有两个长期状态：

- `taxi_dag_type[taxi_id]`：该车辆绑定的微服务 DAG 类型。
- `taxi_dag_assignments[taxi_id][microservice_node]`：该 DAG 每个节点当前部署在哪个边缘服务器。

### 3.2 初始部署

车辆第一次出现时，不触发迁移决策，而是：

1. 调用 `find_k_nearest_servers(..., k=1)` 找到最近边缘服务器。
2. 调用 `assign_dag_type()` 按 `MICROSERVICE_DAGS` 中的概率随机选择 DAG 类型。
3. 调用 `initialize_dag_assignment(dag_type, nearest_server_id)` 将该 DAG 的全部微服务节点共置到最近服务器。

这相当于把首次出现视为服务初始化，而非迁移事件。

### 3.3 微服务 DAG

当前 `core/microservice_dags.py` 定义了 12 类 DAG，覆盖数据密集、计算密集、IoT 轻量、Fan-in、Fan-out、Diamond 等拓扑形态。

每个 DAG 包含：

- `probability`：车辆首次出现时被分配到该 DAG 的概率。
- `nodes`：微服务节点字典，每个节点包含：
  - `image_mb`：镜像大小。
  - `state_mb`：状态数据大小。
  - `is_stateful`：是否有状态服务。
- `edges`：DAG 边及流量权重，形如 `(src, dst): traffic`。

这些边权被奖励函数和图状态构建使用，用于表示微服务间调用强度。跨服务器部署高流量边会增加通信和 tearing 成本。

### 3.4 DAG 工具函数

`core/dag_utils.py` 提供：

- `get_entry_nodes(dag_info)`：返回入度为 0 的节点，作为用户访问 DAG 的入口候选。
- `topological_sort(dag_info)`：Kahn 算法做拓扑排序，DQN 和 Hybrid SAC 按该顺序遍历微服务节点。
- `assign_dag_type()`：按概率随机分配 DAG。
- `initialize_dag_assignment(...)`：初始时将所有节点放到同一服务器。

入口节点用于计算用户到服务网关的距离，也是 SLA 违规判断和奖励中接入延迟的基础。

### 3.5 候选服务器

`core/geo.py` 中的 `find_k_nearest_servers(...)` 基于 Haversine 距离返回最近的 `k` 个边缘服务器，当前三类主算法均使用 `k=3`。

实现上使用 NumPy 向量化和 `argpartition` 加速近邻选择，返回：

```text
(edge_server_id, distance_km, latitude, longitude)
```

## 4. 轨迹预测实现

### 4.1 当前实际使用的预测器

当前迁移算法实际接入的是 `prediction/simple_predictor.py` 中的 `SimpleTrajectoryPredictor`。

训练阶段：

- 对每辆训练集出租车按时间排序。
- 只使用轨迹点不少于 100 的车辆。
- 计算经度差分 `dx = np.diff(lons)` 和纬度差分 `dy = np.diff(lats)`。
- 保存每辆车的平均 `(mean_dx, mean_dy)`。

预测阶段：

- 如果 `taxi_id` 在训练集中见过，则从当前位置开始，每一步累加该车历史平均经纬度增量。
- 默认预测步长由 `FORECAST_HORIZON=15` 控制。
- 输出是 `(lon, lat)`，算法内部会转换成 `(lat, lon)` 传给上下文和奖励函数。

### 4.2 未见车辆的本地运动学兜底

由于训练 / 测试按车辆 ID 拆分，推理阶段 `test_df` 中的车辆通常不会出现在 `predictor.velocity_factors` 中。因此预测器有一个未见车辆兜底分支：

1. 仿真循环通过 `taxi_last` 维护每辆车上一位置、上一时间和上一 episode。
2. `build_predict_future_time_kwargs(...)` 根据当前行和上一行构造 `prev_lon/prev_lat/prev_time/current_time`。
3. 如果当前点与上一点属于不同 episode，或时间差无效，则返回原地预测。
4. 否则计算局部速度：

```text
v_lon = (current_lon - prev_lon) / dt_prev
v_lat = (current_lat - prev_lat) / dt_prev
```

然后按时间步外推未来位置。

该机制使测试集未见车辆仍能基于最近两点做短期预测，而不是完全依赖训练车辆的平均速度。

### 4.3 episode 对预测的影响

`episode_id` 的作用是阻断长时间间隔造成的错误速度估计。若当前行与上一行 episode 不同，预测器不会用跨 episode 的位移估计速度，而是保持原地预测。这避免把长时间停顿、数据缺口或跨轨迹段跳转误解为高速移动。

### 4.4 其他深度预测模型

`prediction/` 下还存在 `lstm.py`、`gru.py`、`cnn.py`、`cnn_lstm.py`、`stt_fnn.py`、`spatioformer.py`、`agentformer.py` 等模型文件。这些更像轨迹预测研究或对比模型，目前没有被 `run_comparison.py` 的主迁移仿真调用。

因此，当前微服务迁移实验中的“轨迹预测”应理解为轻量速度外推模型，而非深度轨迹预测模型。

## 5. 上下文感知与触发机制

### 5.1 Reactive 触发

`core/context.py` 中的 `check_sla_violation(...)` 同时考虑两类条件：

1. 空间距离条件：

```text
dist_km > 15.0
```

2. QoS 接入时延条件：

```text
calc_access_latency_ms(dist_km) > USER_SLA_TOLERANCE_MS
```

其中：

- `DISTANCE_THRESHOLD_KM = 15.0`
- `calc_access_latency_ms(distance) = distance / 200 + 2.0`
- `USER_SLA_TOLERANCE_MS = calc_access_latency_ms(15km) * 0.99`

因为 QoS 容限略小于 15km 对应时延，所以 QoS 条件会在接近 15km 前提前触发。当前 DQN 和 Hybrid SAC 的违规计数使用 `check_sla_violation(...)`；SA 中的 `total_violations` 仍直接统计 `gateway_dist > 15.0`，这一点是当前实现中需要注意的口径差异。

### 5.2 Proactive 触发

`get_trigger_type(...)` 先判断当前是否已 reactive violation：

- 如果当前已经违反 SLA，返回 `TRIGGER_REACTIVE`。
- 如果没有当前违规，并且启用了 proactive 且存在预测轨迹，则检查未来是否会触达 SLA 阈值。

未来判断由 `_ttv_seconds_to_sla_breach(...)` 完成：

```text
ttv_s = 第一次预测距离 >= 15km 的时间
如果 ttv_s <= estimated_migration_time + 1s，则返回 PROACTIVE
```

当前常量为：

- 默认预测步长时间：`60s`
- 估计迁移耗时兜底：`2s`
- 判定条件：`ttv_s <= 3s`

这意味着当前参数下 proactive 触发条件非常严格：预测轨迹的最早一步被视为 60 秒后，而迁移耗时窗口只有约 3 秒。若实验中 proactive 决策数量异常偏低，需要优先检查这里的时间尺度是否符合预期。

### 5.3 图状态中的触发上下文

Hybrid SAC 使用 `build_graph_state(...)` 构造图状态，其中 `trigger_context` 是 3 维：

```text
[proactive_flag, reactive_flag, risk_ratio]
```

- Proactive：`[1.0, 0.0, risk_ratio]`
- Reactive：`[0.0, 1.0, 1.0]`

`risk_ratio = max_entry_dist / 15km`，截断到 `[0, 1]`。它让模型不仅知道“触发类型”，还知道当前风险接近 SLA 阈值的程度，用于缓解过早迁移或过晚迁移的问题。

### 5.4 当前上下文感知的范围

当前实现中的上下文包括：

- 当前用户位置和时间。
- 用户到 DAG 入口节点所在服务器的距离。
- QoS 接入时延。
- 预测未来轨迹。
- 微服务 DAG 节点属性和拓扑流量。
- 触发类型和风险比例。
- SA 给出的先验建议。

当前没有把健康数据、用户画像或服务资源容量纳入主线迁移决策。

## 6. 奖励与成本模型

所有主算法最终都调用 `core/reward.py` 的 `calculate_microservice_reward(...)`，这保证 SA、DQN、Hybrid SAC 在优化目标上大体一致。

### 6.1 总成本组成

奖励函数返回：

```text
reward = max(-total_cost_ms / 1000.0, -10.0)
```

其中 `total_cost_ms` 是真实毫秒成本，主要由六部分构成：

```text
total_cost_ms =
    access_latency_ms
  + migration_delay_ms
  + tearing_delay_ms
  + comm_delay_ms
  + future_delay_ms
  + sla_penalty_ms
```

奖励被缩放到约 `[-10, 0]` 区间，便于神经网络训练；报告和成本拆分仍保留毫秒单位。

### 6.2 接入时延

接入时延取用户到所有入口节点部署服务器的最大距离：

```text
access_latency_ms = max_entry_dist_km / 200 + 2.0
```

这样多入口 DAG 会按最差入口计算用户侧接入压力。

### 6.3 迁移成本

若某个微服务节点从旧服务器迁到新服务器，则计算：

```text
transfer_ms = (image_mb + state_mb) * 8 / effective_bandwidth_mbps * 1000
delta_ms = transfer_ms + 200
```

Reactive 触发下还会乘以：

```text
REACTIVE_MIGRATION_MULT = 1.5
```

这体现了 Reactive 场景下同步迁移、停机和紧急恢复成本更高；Proactive 场景下有更多后台同步空间，迁移成本相对低。

`effective_bandwidth` 由风险比例插值得到：

```text
50Mbps -> 500Mbps
effective_bandwidth = 50 + (500 - 50) * risk_ratio^2
```

距离 SLA 越近，风险越高，假设系统会投入更高迁移带宽。

### 6.4 DAG tearing 与内部通信成本

对每条 DAG 边 `(src, dst)`：

- 如果两个微服务部署在同一服务器，不产生跨边缘成本。
- 如果跨服务器部署：
  - `tearing_delay_ms` 根据边流量、RPC 大小、回传带宽估算。
  - `comm_delay_ms` 根据服务器间 Haversine 距离和流量归一化权重估算。

这使算法不仅追求用户到入口节点更近，也要避免把高流量强依赖节点拆得太散。

### 6.5 Future penalty

当存在预测轨迹和入口节点时，奖励函数会计算未来每个预测点到入口节点部署服务器的最大距离。超过 `15km` 的部分通过传播延迟转换为 `future_delay_ms`，并按 `FUTURE_DECAY=0.9` 衰减加权。

这让 proactive 模式下的算法可以为未来位置提前优化，而不是只对当前点做反应。

### 6.6 SLA penalty

如果当前空间距离或 QoS 时延触发 SLA violation，则额外加入：

```text
SLA_PENALTY_MS = 5000.0
```

这是一项强惩罚，用于让模型优先避免用户可感知的服务质量下降。

## 7. 状态表示

### 7.1 DQN 的 16 维节点状态

`build_node_state(...)` 为 DQN 针对每个微服务节点构造 16 维向量：

```text
[0-5]   全局特征：lat, lon, gateway_dist, hour, weekday, n_candidates
[6-9]   节点特征：image_mb, state_mb, is_stateful, node_traffic_ratio
[10-13] 拓扑特征：neighbor_same_server_ratio, node_server_dist, is_entry, dag_size
[14-15] 移动趋势：avg_delta_lat, avg_delta_lon
```

这些特征把用户位置、时间、候选数量、节点成本、拓扑邻居、当前部署位置和预测移动方向合并到单节点决策中。

### 7.2 Hybrid 的图状态

`build_graph_state(...)` 为 Hybrid SAC 构造结构化图输入：

- `node_features`：形状 `(N, 3)`，每个节点为 `[image_mb/200, state_mb/256, is_stateful]`。
- `adj_matrix`：形状 `(N, N)`，由 DAG 边流量归一化得到，并加入 self-loop。
- `trigger_context`：3 维触发上下文 `[proactive, reactive, risk_ratio]`。
- `sa_priors`：形状 `(N, 2)`，每个节点为 `[SA 建议服务器到用户距离 / 50, SA 是否建议保持当前部署]`。
- `node_names`：固定排序后的节点名，用于索引映射。

这使 Hybrid SAC 可以同时感知 DAG 全局结构、触发类型和 SA 草案。

## 8. 实际迁移算法

当前主实验比较三类算法：SA、DQN、Hybrid SAC。它们共享相同的数据、DAG、候选服务器、触发和奖励接口，但决策方式不同。

### 8.1 Simulated Annealing

文件：`algorithms/sa.py`

核心函数：

- `microservice_simulated_annealing(...)`
- `run_sa_microservice_fair(...)`

单次迁移触发时，SA 在整个 DAG 的节点部署空间上搜索：

1. 当前解为当前 DAG 全部节点的部署。
2. 每轮随机选一个微服务节点。
3. 从最近 `k=3` 候选服务器中随机选一个不同服务器作为邻居动作。
4. 调用统一奖励函数计算邻居成本。
5. 如果邻居更优则接受；否则按 `exp(-delta / temp)` 概率接受。
6. 温度按 `cooling_rate=0.97` 降温。
7. 默认 `temp=3000.0`、`max_iter=50`。

SA 输出的是整张 DAG 的 `best_assignments`。它不学习参数，是优化型基线；优点是目标函数清晰，缺点是每次触发都要迭代评估多个邻居，决策时延较高。

### 8.2 DQN

文件：`algorithms/dqn.py`

核心类和函数：

- `MicroserviceDQN`
- `optimize_model(...)`
- `run_dqn_microservice_fair(...)`

网络结构：

```text
Input(16)
  -> Linear(128) -> ReLU
  -> Linear(128) -> ReLU
  -> Linear(4)
```

动作空间为 4 个离散动作：

```text
0: 保持当前服务器
1: 迁移到最近候选服务器
2: 迁移到第二近候选服务器
3: 迁移到第三近候选服务器
```

单次触发时，DQN 按 DAG 拓扑序遍历每个微服务节点：

1. 为当前节点构造 16 维状态。
2. 用 epsilon-greedy 选择动作。
3. 立即更新该节点部署。
4. 整个 DAG 决策完成后调用统一奖励函数。
5. 将节点级 transition 放入 replay buffer。
6. 训练模式下从 replay buffer 采样，使用 target network 做 TD 更新。

主要训练配置：

- Replay buffer：`maxlen=5000`
- Batch size：`32`
- 折扣因子：`gamma=0.95`
- 初始 epsilon：`0.3`
- epsilon 衰减：`0.995`
- 最小 epsilon：`0.01`
- Target network 更新频率：每 50 次决策
- 优化器：Adam，学习率 `0.001`

训练后可保存 checkpoint；推理模式加载 checkpoint 并设置 `epsilon=0.0`，做确定性贪心动作选择。

### 8.3 Hybrid SAC

文件：`algorithms/hybrid_sac.py`

这是当前最复杂的主算法，可以理解为：

```text
SA 全局草案
  + Trigger-Aware Graph Attention
  + Discrete Soft Actor-Critic
  -> 对每个微服务节点做精炼动作
```

核心组件：

- `TriggerAwareGAT`：触发感知图注意力网络。
- `SACDiscreteActor`：离散策略网络，输出动作概率或 masked logits。
- `SACDiscreteCritic`：双 Q 网络，降低 Q 值高估。
- `optimize_sac(...)`：离散 SAC 训练。
- `run_hybrid_sac_microservice(...)`：完整仿真和训练循环。

Hybrid SAC 的动作空间为 3 个：

```text
0: STAY，保持当前节点部署
1: FOLLOW_SA，采用 SA 对该节点的建议
2: NEAREST，迁移到当前最近服务器
```

动作掩码中 `STAY` 和 `FOLLOW_SA` 恒合法；`NEAREST` 需要至少一个候选服务器。若出现全非法行，会回退到 `FOLLOW_SA`，避免 softmax NaN。

单次触发流程：

1. 调用 `microservice_simulated_annealing(...)` 得到整张 DAG 的 SA proposal。
2. 调用 `build_graph_state(...)` 构造图状态。
3. GAT 根据节点特征、DAG 邻接矩阵和触发上下文生成节点 embedding。
4. 按拓扑序遍历节点。
5. Actor 针对每个节点在 `STAY / FOLLOW_SA / NEAREST` 中选择动作。
6. 更新节点部署。
7. 调用统一奖励函数计算 DAG 总 reward。
8. 将每个节点 transition 写入 replay buffer。
9. 训练模式下执行 SAC 更新和 target critic soft update。

### 8.4 TriggerAwareGAT 的关键设计

GAT 不只是普通图网络，而是把触发类型显式注入每个节点：

1. 将 `trigger_context` broadcast 到所有节点，并与节点特征拼接。
2. 通过多头注意力在 DAG 拓扑上做消息传递。
3. 使用 trigger temperature 控制注意力锐度。
4. 使用 trigger gate 调节注意力强度。
5. 使用 stateful-trigger bias 建模“有状态节点在 Reactive 下迁移更昂贵”的不对称性。

物理直觉是：

- Proactive：系统有提前量，可以更主动考虑有状态节点迁移和全局拓扑优化。
- Reactive：SLA 已经出问题，应更关注关键路径和入口，避免昂贵的有状态同步迁移。

### 8.5 Hybrid SAC 训练策略

当前训练默认多 epoch：

- `num_epochs=6` 表示 5 个训练 epoch + 1 个最终 eval epoch。
- 最后一轮 eval 会清空 DAG/轨迹缓存，从干净的 nearest 初始部署开始。
- eval epoch 使用 deterministic argmax，不执行 replay、优化或 soft update。
- `inference_mode=True` 时只运行 1 个 eval epoch，并加载 checkpoint。

行为克隆课程学习：

- Proactive schedule：`[0.95, 0.85, 0.65, 0.35, 0.10]`
- Reactive schedule：`[0.98, 0.90, 0.75, 0.55, 0.30]`

训练早期更高概率强制 `FOLLOW_SA`，让策略先学习 SA 基线；后期逐步交给 Actor 自主探索。Reactive 下衰减更慢，因为 Reactive 迁移成本更高、策略更容易保守或坍塌。

SAC 关键超参：

- embedding dim：`64`
- hidden dim：`64`
- actor hidden：`128`
- critic hidden：`128`
- learning rate：`3e-4`
- `alpha_init=0.001`
- `gamma=0.95`
- `tau=0.005`
- replay buffer：`10000`
- batch size：`32`
- target entropy：`0.90 * log(3)`

此外，Hybrid SAC 对 proactive 触发后设置了一个简单防抖锁：

```text
migration_lock[taxi_id] = sim_step + 2
```

用于避免同一车辆连续 proactive 触发导致过于频繁迁移；Reactive 仍可绕过 proactive gate。

## 9. 训练、推理和评估输出

### 9.1 运行模式

`run_comparison.py` 支持两种主模式：

1. 普通模式：
   - 由 `INFERENCE_MODE` 控制训练或推理。
   - 运行 proactive 与 reactive 两组实验。
   - 生成 `result.md`。

2. `--pipeline` 模式：
   - 删除旧 SAC proactive/reactive checkpoint。
   - 在 `train_df` 上训练 SA、DQN、Hybrid SAC。
   - 保存 DQN 和 SAC 权重。
   - 在 `test_df` 上加载权重推理。
   - 生成合并版 `result.md`。
   - 输出训练曲线、成本拆分、违规对比图。

### 9.2 Proactive 与 Reactive

每个算法都分别跑 proactive 和 reactive：

- Proactive：传入已拟合预测器，允许基于预测轨迹提前触发迁移，并在 reward 中加入 future penalty。
- Reactive：不使用预测触发，主要基于当前 SLA violation 做迁移。

对比目标是观察主动迁移是否能减少真实 SLA 违规，以及为此付出了多少迁移成本。

### 9.3 指标

每个算法返回的主要结果包括：

- `total_migrations`：迁移的微服务节点总数。
- `total_violations`：真实 SLA 违规次数。
- `proactive_decisions`：Proactive 触发次数。
- `decision_count`：总触发决策次数。
- `total_reward`：累计 reward。
- `total_access_latency`：累计接入时延。
- `total_communication_cost`：累计内部通信成本。
- `total_migration_cost`：累计迁移成本。
- `loss_history` / `reward_history` / `entropy_history` 等训练曲线数据。
- `avg_decision_time_ms`：平均单次触发决策时延。
- `dag_proactive_migration_stats`：推理阶段可按 DAG 类型统计 proactive 决策和迁移节点数。

排行榜使用：

```text
Score = Migrations + 0.5 * Violations
```

分数越低越好。这是实验展示指标，不等同于训练 reward；训练 reward 使用物理总成本毫秒缩放。

### 9.4 输出文件

主要输出包括：

- `result.md`：实验报告。
- `outputs/dqn_*_training.png`：DQN 训练曲线。
- `outputs/hybrid_sac_*_training.png`：Hybrid SAC 训练曲线。
- `outputs/cost_breakdown.png`：成本拆分。
- `outputs/violation_comparison.png`：Proactive / Reactive 违规对比。
- `checkpoints/*.pth`：训练后的 DQN / SAC 权重。

## 10. 当前实现特点与注意点

### 10.1 当前实现的主要优点

- 已经从单体服务迁移升级为 DAG 微服务协同迁移。
- 三个算法共享统一数据、DAG、触发和奖励接口，对比口径较清晰。
- 奖励函数纳入接入、迁移、内部通信、tearing、future、SLA penalty，多维度比简单距离阈值更接近微服务迁移场景。
- Hybrid SAC 引入 SA prior，避免纯 RL 从零探索整个 DAG 放置空间。
- TriggerAwareGAT 显式建模触发类型、风险程度、有状态节点和 DAG 边流量。
- 训练 / 推理按车辆 ID 80/20 拆分，且推理预测器只在训练集拟合，具备一定泛化评估意识。
- 关键距离和近邻计算已做 NumPy 向量化，降低仿真开销。

### 10.2 需要特别关注的实现口径

1. SA 与 DQN/Hybrid SAC 的违规计数口径不完全一致。SA 当前使用 `gateway_dist > 15.0`，DQN 和 Hybrid SAC 使用 `check_sla_violation(...)`，后者还包含 QoS latency 条件。

2. Proactive 触发时间尺度可能过严。当前 `ttv_s` 的最小预测时间是 60 秒，而迁移耗时窗口约 3 秒，这可能导致真正的 `TRIGGER_PROACTIVE` 很难发生。若目标是研究主动迁移，应重新校准 `_DEFAULT_FORECAST_STEP_DT_SEC` 和 `_ESTIMATED_MIGRATION_TIME_S_FALLBACK`。

3. 当前健康上下文没有进入主线算法。原始数据里的健康字段在 `load_data(...)` 中被丢弃，当前“上下文感知”主要是物理/QoS/预测/DAG/触发上下文。

4. DQN 的 credit assignment 仍较稀疏。它将整个 DAG 的 reward 主要放在最后节点 transition 上；Hybrid SAC 已改为每个节点共享 `reward / num_nodes` 的 dense reward。

5. DAG 资源容量约束尚未建模。当前没有 CPU、内存、带宽容量上限，也没有边缘服务器负载约束。

6. 当前 DAG 分配是随机按概率给 taxi 绑定，未根据用户业务类型或实际请求序列决定 DAG。

7. 深度轨迹预测模型尚未接入迁移决策。当前迁移仿真仍使用简单速度外推和本地运动学兜底。

### 10.3 后续改进方向

- 统一 `total_violations` 的统计口径，让 SA、DQN、Hybrid SAC 全部使用同一 SLA 判断。
- 重新标定 proactive TTV 触发条件，使预测时间步、迁移耗时和轨迹采样间隔一致。
- 将健康、用户优先级或业务 SLA 等非物理上下文重新纳入状态和触发逻辑，但要避免与 reward 口径混淆。
- 为边缘服务器加入资源容量和负载约束，防止所有节点过度集中到最近服务器。
- 将 `prediction/` 中更强的深度轨迹模型接入 `SimpleTrajectoryPredictor` 的接口，做可替换预测器实验。
- 对 Hybrid SAC 做消融实验：无 SA prior、无 trigger_context、无 risk_ratio、无 GAT、不同 reward scaling。
- 对迁移成本参数做灵敏度分析：`BASE_MIGRATION_OVERHEAD_MS`、`REACTIVE_MIGRATION_MULT`、`SLA_PENALTY_MS`、`FUTURE_DECAY`。

## 11. 一句话总结

当前代码库已经形成了一条较完整的微服务迁移实验链路：先对出租车轨迹做清洗和按车拆分，再用轻量轨迹预测提供未来位置，在时间步仿真中为每辆车维护一个微服务 DAG，通过物理 SLA 和预测上下文触发迁移，最后用 SA、DQN、Hybrid SAC 三类算法在候选边缘服务器上更新 DAG 节点放置，并用统一的毫秒级成本模型评估接入质量、迁移开销、DAG 内部通信和 SLA 违规。
